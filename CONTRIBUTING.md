## Rules

Every rule lives in `lib/sandhi/<group>/apply-<rule>/` and exports:

- `report`: `() => 'name of the sūtra'`
- `nimitta` (optional), then `shraum` or `karya`.

Text is SLP1. Conditions are flat: no `&&` or `||` in `nimitta`, use negated
guards, named built-ins and lookups. Fixtures are `name.js` (input `a, b;`) and
`name-fix.js` (generated with `UPDATE=1 bun run test`). The sūtra number of a
rule is documented in the README rule list.

## Simplicity

Simple code is easier to read, test and support than clever code. Before
adding something, check what already exists.

- Use what 🐊Putout already gives. Switching rules on and off, per-rule
  options and the fix loop are Putout features: pass `rules` to `putout`,
  register an optional rule as `['off', rule]`, read `options` in a runner.
- Do not build a second engine on top of the first one: no running the
  whole text several times, no trying every on/off combination of rules, no
  collecting "variants", no new rule exports that only a custom loop reads.
  Such code is slow, hard to understand and hard to cover with tests.
- One rule is one sūtra. A rule does not repeat another rule's condition in
  its guards. When two rules meet on the same pair, give the first rule a
  solo case that leaves the pair to the second one.
- Prefer a guard, a case order or a small named built-in to new runner
  code. Change a runner only when a failing test shows a rule cannot be
  written without it.
- If a change needs a long explanation, look for a simpler change.

## Commit

Format of the commit message: **type: scope: subject**

**Type**:

- **feature: scope: subject**
- **fix: scope: subject**
- **docs: scope: subject**
- **refactor: scope: subject**
- **test: scope: subject**
- **chore: scope: subject**

**Scope**:
Scope could be anything specifying place of the commit change.
For example util, console, view, edit, style etc...

**Subject text**:

- use imperative, present tense: “change” not “changed” nor “changes”
- don't capitalize first letter
- no dot (.) at the end
  **Message body**:
- just as in <subject> use imperative, present tense: “change” not “changed” nor “changes”
- includes motivation for the change and contrasts with previous behavior

Do not add `Co-Authored-By`, "assisted by", "generated by" or any other
attribution line to commit messages or PR descriptions.
